DESIGN REVIEW — not implemented

NE Trip Planner

A shared-session travel bot for Northeast India. Open a link, invite friends with a code, plan together with a bot grounded in a curated knowledge base. POC in pocs/ne-trip-planner/.

1 · Goal & confirmed decisions

Relation to Oxomiai

New standalone POC. Reuses Oxomiai's KB JSONL + schema as seed, own backend.

Geography

All 8 NE states, Assam deepest. ~40 new KB entries for the 7 other states.

Join model

No login. Open link → session. Others join via 6-char code + display name.

Cloud

Cloud-agnostic: container + Postgres(pgvector) + Anthropic API. Maps to AWS/GCP/Fly/Render.

Hypothesis

A group converges on a concrete itinerary in one sitting; ≥80% grounded answers; fan-out p95 < 1 s.

Out of scope

Accounts, payments, bookings, live transport, maps, voice, offline, multi-language.

2 · Architecture

Cross-instance fan-out uses Postgres LISTEN/NOTIFY, so the POC needs no Redis yet still runs on N instances.

4 · Key flows

Create & join

  1. Open / → server creates session + code, redirects to /s/K7M4QX.
  2. Enter display name once; participant token saved on device.
  3. Copy link/code to friends. They open it (or type the code on the home page), set a name.
  4. WebSocket connects; snapshot of chat + plan arrives; presence updates.

One bot turn

  1. Messages from any member are stored and broadcast instantly.
  2. Turn lock: if the bot is busy, new messages queue and are batched into the next turn.
  3. Orchestrator builds prompt: rules + participants/prefs + current plan + recent chat.
  4. Claude calls search_kb / get_weather / update_plan; tokens stream to all clients.
  5. update_plan is validated, versioned and broadcast; the plan panel updates live.

5 · Knowledge & RAG

Ingest

JSONL (Oxomiai seed + new states) and markdown guides (permits, seasons, transit hubs, itineraries, budgets) → 300–500-token chunks → local bge-small embeddings → kb_chunks with state, type, season, source, last_verified, high_risk.

Retrieve

Hybrid: pgvector similarity + Postgres full-text, fused by RRF, metadata-filtered. Corpus is a few hundred chunks — no managed vector DB needed.

Guardrails

No place/permit/season fact without a tool result. Chunks cite kb_id and date; permit/season answers end with “verify before travel”. Unknown → “I don't have that.”

Why Postgres+pgvector

Already needed for sessions; portable across all clouds; one thing to run. Revisit (OpenSearch/Vertex) only if the corpus grows by orders of magnitude.

8 · Safety & limits

  • Per-session token budget + message rate limit; max 8 participants; 14-day idle TTL; any member can delete the session.
  • Join/code attempts rate-limited; tokens stored hashed; ≥128-bit participant tokens.
  • KB text and chat are delimited data, never instructions; the bot's only write tool touches the plan.
